# VEP-0002: Precondition-evaluation contract v1

- Status: Accepted
- Contract identifier: `veyra.preconditions/v1`
- Protocol: `veyra.protocol/v1` (unchanged)
- Authors: Veyra contributors
- Date: 2026-09-24

## Abstract

VEP-0001 reserved `Effect.preconditions` and V0.1 rejected every non-empty list rather than
pretending to evaluate it. This VEP defines the first bounded, versioned evaluation contract:
which `Condition` kinds are meaningful before a side effect, where evaluation sits in the
transaction lifecycle, and what honest failure produces. The surface is deliberately minimal —
only deterministic local-state observations that can be checked inside the trust boundary with
resources the effect already declares.

A precondition is an observation constraint, never authority. It cannot grant, widen, or rescue
capability, approval, containment, idempotency, or verification semantics; a satisfied
precondition only permits the normal authority and staging pipeline to continue.

## Contract surface

`veyra.preconditions/v1` supports exactly these `Condition` kinds in `Effect.preconditions`:

- `file_exists { path, expected }` — the path does or does not name an existing filesystem
  entry.
- `file_sha256 { path, digest }` — the path names a regular file whose content hashes to the
  lowercase hex `digest`.

Every other `Condition` kind — `http_status`, `output_sha256`, and `custom` — is **invalid** as
a precondition: those kinds describe the outcome of a side effect that has not happened or an
evaluation that has no deterministic contract, so plan validation rejects them rather than
ignoring them. Unknown kinds fail closed the same way. A contract revision that widens the
evaluated surface must use a new identifier and a new VEP.

Rules that apply to every supported kind:

- Condition lists are bounded by the kernel's `maximum_conditions_per_effect` limit and must not
  contain duplicates.
- Every condition path must reference exactly one of the paths in the effect's declared
  `resource`. A precondition can never observe outside the resource the effect is already
  authorized for; this is shape-checked at plan validation and re-enforced by the adapter at
  evaluation time under the same no-follow containment used for postconditions.
- Condition text is public evidence — never secret material — and all evidence stays inside the
  bounded-adapter-evidence budget.

## Lifecycle placement and atomicity

Evaluation is a gate inside `run_transaction`, in this order:

1. The transaction must be `approved`.
2. The kernel reloads the journaled preflighted plan and re-evaluates live policy over the exact
   effect — capability status, expiry, remaining uses, and approval expiry — before any
   precondition is observed. Revoked or expired authority fails closed here without evaluating
   anything.
3. Each effect's adapter evaluates its declared preconditions read-only via
   `EffectAdapter::check_preconditions`. Effects with empty precondition lists produce no event.
4. Only when every declared precondition passes does the transaction proceed to staging, where
   capability uses and approval nonces are consumed atomically as before.

Because the gate runs before `consume_authority`, a failed precondition never burns capability
uses, approval nonces, idempotency reservations, or staging evidence. Evaluation itself is a
point-in-time observation — it does not lock the workspace. The residual check-to-stage race is
the same documented TOCTOU window the rest of the pipeline already re-observes under its own
containment and digest checks; preconditions narrow an authorized execution, they do not freeze
external state.

## Failure semantics

A false condition, an adapter error, an out-of-scope condition, and malformed or incomplete
adapter evidence all produce the same honest outcome:

- one `effect.preconditions_evaluated` audit event per evaluated effect carrying the contract
  identifier, the per-condition `passed` results, and bounded check messages;
- a single `approved → precondition_failed` transition recorded as
  `transaction.precondition_failed` with the failing effect IDs;
- no staging, no execution, no receipts, and no authority consumption.

`precondition_failed` is a terminal state: it has no outgoing edge, is excluded from recovery
classification (nothing executed, so nothing needs recovery), and is a final state for
staging-artifact retention. It is distinct from `denied` (policy refused the proposal before
evaluation) and from `failed` (a side-effect boundary was crossed). Re-running the transaction
is rejected rather than silently re-evaluated.

When an adapter cannot produce trustworthy evidence — an unimplemented `check_preconditions`,
a containment breach, I/O failure, or checks that do not match the declared conditions — the
kernel records a bounded `veyra.adapter.precondition_error/v1` check row with `passed: false`
instead of adapter-supplied text, so a misreporting adapter can only ever cause refusal.

## Adapter contract

`EffectAdapter::check_preconditions(effect, context)` returns one `VerificationCheck` per
declared precondition, in order; a false condition is a check with `passed: false`, and only an
unobservable or out-of-contract condition is an `AdapterError`. The bundled filesystem adapter
implements the contract for `file_exists` and `file_sha256`. The default trait implementation
fails closed, and adapters that do not implement the contract must keep rejecting non-empty
`preconditions` in `validate`, so HTTP, process, and custom adapters retain their prior
fail-closed behavior.

## Compatibility

- `TransactionState` gains the serialized value `precondition_failed`; readers that enumerate
  states must be updated. Generated JSON Schemas are regenerated byte-for-byte and a committed
  fixture pins the wire value.
- Plans that declared non-empty preconditions were previously invalid and could never reach the
  journal, so no persisted plan changes meaning; older readers simply reject the new state value
  rather than misinterpreting it.
- `veyra.protocol/v1` is unchanged: the new surface is a separable contract version, and the
  precondition contract identifier is recorded in every evaluation event.

## Security considerations

The gate preserves the security invariants: planners remain untrusted, conditions are
shape-validated before adapter dispatch, evaluation observes only declared resources, and every
unsupported or ambiguous condition fails closed. The new failure state and events are journaled
and hash-chained like every other transition. Residual risks: precondition observation is not
atomic with the later execution, and filesystem state may change between evaluation and staging;
adapters re-observe that state at each later boundary, and the gap is documented here rather
than hidden.
